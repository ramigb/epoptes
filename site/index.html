Long agent runs.
Under watch.

Epoptes runs the long jobs you'd love to hand to an agent overnight: a feature build, a research sweep, a stack of documents, a data clean-up. You describe the goal in a chat. Epoptes runs it as a series of fresh-context cycles in a time box, with a live dashboard, a board you steer it through, and a report in the morning.

ἐπόπτης, “the overseer”: a title for Zeus and Helios, who watch over everything.

01 · what it is

A skill, a runner, a dashboard.

Three small parts that share nothing but a folder of plain files, .epoptes/, in your project. Any of them can be replaced, and you can read or fix every file by hand.

  1. 1

    The skill designs the harness

    Ask your agent to “use the epoptes skill”. It interviews you about the outcome, a done definition it can check, the time box, the team and what always needs your approval. Then it writes the harness and checks it with a dry run.

  2. 2

    The runner runs it in cycles

    A detached process per goal. Each cycle starts your own claude, codex, pi or agy with a fresh context. The cycle orients from small state files and the board, does a slice of work, verifies it, records it and exits.

  3. 3

    The dashboard lets you watch and steer

    epoptes ui on 127.0.0.1. A live ticker, a kanban board for feedback, approvals to answer, the clock, costs and plan usage, then a report. Closing it never stops a run.

02 · why

Long sessions drift. Short cycles don't.

Epoptes grew out of a 12-hour autonomous game build: 19 cycles, about $186 of API-equivalent usage, and a notebook of what went wrong. Its rules for keeping long runs cheap and on track are built in, so you don't have to relearn them.

One context fills up, gets summarised, and forgets what failed.

1 A fresh context every cycle

Memory lives in small files the next cycle reads first: a 25-line handoff, a progress table, lessons and decisions. Nothing drifts out of a summary, and every cycle starts sharp.

Every step costs the price of the most expensive model.

2 Cheap models for mechanical work

A team of roles, each with its own model: a strong orchestrator and reviewer, mid-size workers, and a small checker that only runs tests and reports facts.

Notes grow until reading them is the job.

3 State files with size caps

Each state file has a line cap the dry run and the runner check. Orienting takes six tool calls or fewer, with targeted reads instead of whole files.

A single run can wander for hours with nothing to show.

4 A time and round cap per cycle

A cycle does at most three rounds of one to three tasks, under a soft time cap and a hard timeout. A fresh cycle is cheaper than a bloated one.

          04 · crash course

          From a sentence to a morning report.

          Seven steps. The first two take a few minutes; the rest is the run looking after itself.

          Install Epoptes and give your agent the skill

          You need Node.js 22.18 or newer, Linux, macOS or WSL2, and at least one agent CLI installed and logged in. Epoptes runs your own CLI and never handles logins or keys.

          The skill is how your agent learns to design harnesses. Install it for each CLI you use: it links into that CLI's skills folder.

          terminal
          $ npm install -g @ramigbcom/epoptes
$ epoptes skill install                        # Claude Code
$ epoptes skill install --agent codex          # Codex
$ epoptes skill install --agent pi             # pi
$ epoptes skill install --agent antigravity    # agy

          Describe the goal. The skill interviews you.

          In the folder the work should happen in, ask for a harness. The agent looks around first, then asks only what it can't find out, two to four questions at a time:

          • the outcome, and a done definition it can check
          • non-goals and the time box
          • the team: roles, models and effort
          • checkpoints, and what always needs your approval
          • where the deliverable lives, so the dashboard can link to it

          It reads lessons from your past harnesses and shows a one-screen summary for you to sign off.

          claude
          > use the epoptes skill to build a harness for writing a
  20-page field guide to our internal APIs

● I read the README, the OpenAPI spec and docs/. A few questions:

  1. Done: how would you check it in 2 minutes?
     ❯ every endpoint documented + examples run (Recommended)
       an editor's rubric score ≥ 8 as well
  2. Time box: ❯ 8h active, 45m wrap-up (Recommended)
  3. Team: ❯ writer (sonnet) · factcheck (haiku) · editor (opus)
  4. Always ask before: ❯ publishing anything outside this machine

● Lessons applied from the brain: 2 (fresh-results timestamps,
  parallel tasks own separate files). Summary below; sign off?

          The harness is a folder of plain files

          Everything lives in .epoptes/ next to your work. Commit it, diff it, edit it by hand. Live runner state and per-cycle transcripts are gitignored and never leave your machine.

          Role files become native subagents on Claude Code, Codex and Antigravity, each on its own model. On pi the loop works through them in sequence.

          A dry run checks the guardrails

          epoptes run --dry-run never starts the clock. It validates the goal and prints the exact command the next cycle will run. It also flags:

          • template leftovers
          • missing deny rules and over-broad allows
          • anything that looks like a credential
          • roles with no description or a model the CLI can't use
          • a loop that never reads the board or reports done

          Then epoptes add registers the goal with the dashboard.

          terminal
          $ epoptes run --dry-run

          Press Start, then go to bed

          Open the dashboard and press Start, or start from the terminal. The runner is detached: closing the dashboard or the terminal never stops it.

          Between cycles it checks the clock, your controls, rate limits and failures. Near the end the goal switches to wrap-up (feature freeze), then overtime, then stops. It finishes early once its checks pass.

          Steer through the board, not the transcript

          Your feedback lands in the backlog as a card. The orchestrator triages it into TODO or cuts it with a reason, works it, verifies it in REVIEW and moves it to DONE. Comment on any card; the next cycle acts on it or replies.

          Anything on the approval list waits for your Approve or Disapprove while the run carries on with other work. Need to change course right now? ⚡ Steer now interrupts the cycle, and the next one replans the board around you.

          terminal
          $ epoptes feedback "the intros are too long"
added C-9 to the backlog

$ epoptes card C-4 comment "link the error codes table"
$ epoptes card C-12 approve "internal wiki only"
$ epoptes feedback "drop GraphQL, REST only" --steer
added C-13 (steering): the running cycle is interrupted now
and a fresh one replans around it

$ epoptes extend 1h
$ epoptes pause          # after this cycle

          Read the report, follow up, take the next job

          The report covers what was done, where the time went, tokens and cost per cycle, milestones against the plan, and the handoff. It comes as Markdown and as script-free HTML.

          Small tweaks after DONE go through a follow-up: only your open cards, no time box. The project's next feature is a new job on the same harness, which keeps its roles and lessons. Every run feeds the brain, so the next harness starts smarter.

          terminal
          $ epoptes report
report written:
  ~/work/api-guide/.epoptes/reports/field-guide-20261029-0712.md
  ~/work/api-guide/.epoptes/reports/field-guide-20261029-0712.html

$ epoptes start --follow-up       # fix my open cards
$ epoptes job new "SDK quick-starts"
$ epoptes brain

          05 · features

          Everything a long run needs. Nothing it doesn't.

          • The board

            One kanban board per harness, each job an epic. Cards carry a milestone, a role and a priority. Drag them, comment on them; a comment on a done card reopens it.

          • Steer now

            Interrupts the running cycle. The next one replans the whole board around what you said. Works from a card comment too.

          • Approvals

            What's on the approval list waits for you while the run carries on. Only when nothing else can move does it pause as “waiting for you”, with the reason.

          • A fair clock

            Counts active time only: pauses and rate-limit waits don't count. Wrap-up, overtime, early finish, and a projected finish from the milestone pace.

          • Checkable done

            Two to six done checks: a command that exits 0, a file that must exist, a reviewer scoring against a rubric you wrote together. Few manual ones.

          • A model per role

            Roles run as native subagents on Claude Code, Codex and Antigravity: cheap models for checks, strong ones for review. On pi, any OpenRouter model.

          • Costs and limits

            Tokens by model, cache share and cost per cycle, with cycles over twice the median flagged. Plan usage live. Rate limits wait for the reset.

          • Checkpoints

            Code goals commit each verified task (never push). Anything else gets a shadow git snapshot after every cycle, outside your own repo.

          • The brain

            Lessons from every run, plus each goal's numbers and signals, gathered locally for zero tokens. The skill reads them before designing the next harness.

          • Jobs and follow-ups

            One harness, many jobs over time. After DONE, a follow-up fixes your open cards in place, and flags anything big for a new run.

          • Reports

            Markdown and script-free HTML that open from disk and print. “Where the time went” shows running, rate limits, waiting for you, per role and per tool.

          • Guardrails, local only

            Each CLI's own permissions or sandbox, no push, no secrets in goal files. The dashboard binds to 127.0.0.1, with CSRF and DNS-rebinding guards. No telemetry.

          What Epoptes is and isn't

          epoptes is

          • a local runner for your own logged-in agent CLI
          • for long jobs: an evening, a night, a weekend
          • plain files in your project you can read and fix
          • a personal tool that improves from daily use, MIT licensed

          epoptes isn't

          • a hosted service: no accounts, no telemetry
          • a way around usage limits: it waits for them
          • an agent itself: your CLI does the work
          • finished: early (0.5), and file formats may still change
